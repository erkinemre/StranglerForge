# Phase 05 integration events

Immutable V1 records in `Inventory.Application` describe facts after committed transitions: `InventoryReservedV1`, `InventoryReservationReleasedV1`, `InventoryReservationConfirmedV1`, and `InventoryAdjustedV1`. `InventoryReservationRejectedV1` is a reserved contract for a future rejection consumer; rejected requests currently return a synchronous conflict and do not publish a fact. Each record carries `EventId`, `CorrelationId`, UTC occurrence time, `EventVersion=1`, and relevant reservation, order, product, and quantity fields. A domain event would be an internal aggregate decision; these are external integration contracts persisted in the outbox. Never serialize a domain entity as an event. Add V2 rather than changing V1 field meaning.

Reservation is synchronous because the order command needs a definitive stock result. Events are asynchronous audit facts. The Inventory audit consumer records `InventoryReservedV1` once by EventId; it does not send a second customer notification. HTTP idempotency uses reservation/order IDs and PostgreSQL uniqueness; a retrying order client supplies a GUID `Idempotency-Key` header so the monolith reuses the order ID. Message idempotency uses MassTransit Inbox MessageId plus durable EventId uniqueness. These solve different retry paths.

The broker and Docker runtime were unavailable during local validation. PostgreSQL integration tests used MassTransit's in-memory transport; one test showed state and outbox rows persist while RabbitMQ is unreachable. Real RabbitMQ redelivery and recovery remain unverified.
