# Inventory service ownership and consistency

Inventory owns `StockItems`, `StockReservations`, `InventoryAdjustments`, `InventoryTransactions`, `InventoryAudit`, and MassTransit inbox/outbox tables in its PostgreSQL database. Catalog owns product names and prices in a separate database. Inventory references Catalog product GUIDs and checks product existence through Catalog HTTP before stock additions; it never queries Catalog persistence at runtime. During pre-cutover migration, the one-shot tool checks all source stock and pending-order product IDs against Catalog PostgreSQL. At the Phase 05 boundary, Orders remained in SQL Server with price snapshots. Phase 06 moved Order ownership to Orders PostgreSQL while preserving those snapshots.

`StockItems.Quantity` is physical stock, `Reserved` is pending stock, and `Available = Quantity - Reserved`. The invariant is `0 <= Reserved <= Quantity`. Reservation uses one PostgreSQL transaction and a conditional SQL update of `Reserved` only when enough stock remains. The unique reservation ID and unique order ID indexes prevent duplicate holds. Concurrent duplicate requests race safely: the losing transaction rolls back its stock update, then reads the committed reservation. Release and confirmation conditionally change `Reserved` and reservation status in the same transaction; repeated operations return the existing terminal state. The database, not an in-process lock, enforces contention safety.

MassTransit's EF Core Bus Outbox writes integration events in the same PostgreSQL transaction as stock changes. Its delivery service sends committed rows later; RabbitMQ downtime leaves rows for later delivery. The consumer uses MassTransit's EF Inbox keyed by MessageId and an `InventoryAudit.EventId` uniqueness constraint. Detection is bounded by the configured inbox retention window; business-side EventId uniqueness remains durable. Delivery is at least once, and handlers must remain idempotent. RabbitMQ poison messages exhaust three retries at two-second intervals and move to MassTransit's `_error` queue; unsupported messages go to `_skipped`. Inspect queue depth and, when explicitly enabled with `Inventory:DiagnosticsEnabled=true` on trusted deployments, the `/internal/inventory/outbox` pending count when diagnosing backlog. No customer notification is emitted by this audit consumer.



Callers may provide a GUID `Idempotency-Key` on order creation. The monolith uses that GUID as the order and Inventory reservation ID, so a retry of the same request returns the same order. Reusing it for different customer, product, or quantity produces a conflict. Calls without the header preserve the earlier API behavior and do not have this retry guarantee.
