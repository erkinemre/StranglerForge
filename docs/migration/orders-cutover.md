# Order cutover, migration, and rollback

1. Keep `OrdersOwnership:Mode=Legacy` and YARP order routes on the legacy cluster. Stop order creation and payment writes; drain in-flight requests. Verify Inventory remains authoritative in PostgreSQL. Check SQL order statuses and matching Inventory reservations for every pending order.
2. Create an independent Orders PostgreSQL database and apply the EF migrations in `Orders.Infrastructure`. Set `ConnectionStrings__LegacyCommerce` and `ConnectionStrings__Orders`. Set `ORDERS_WRITE_FREEZE_ACK=true` only after the write freeze. Run `dotnet run --project src/Services/Orders/Orders.Migration -- --import`, then `--verify`, then repeat `--import`. The tool preserves order, customer, and product GUIDs, quantity, unit-price snapshots, and exact historical status text. It rejects divergent or target-only rows and detects source changes during import. SQL has no order timestamps; `CreatedAtUtc` and `UpdatedAtUtc` on imported rows record import time, not original business time.
3. Configure `OrdersInternal__Token` through a secret store on both Orders and LegacyCommerce, plus the Orders database, RabbitMQ, and HTTP dependency addresses. Keep direct internal endpoints private. Deploy both services before switching routes. Verify `/health` and `/health/messaging` separately. Switch the gateway's `orders` and `orderById` routes to Orders together with monolith `OrdersOwnership:Mode=Extracted` under the same freeze. Payment remains routed to LegacyCommerce and is forwarded internally for extracted orders.
4. Reopen writes after a through-gateway order/payment check. The public `POST /api/orders` now returns `201` with an initial `Submitted` status, even if inventory later rejects; poll `GET /api/orders/{id}` for the terminal state. `POST /api/orders/{id}/payment` returns `202` while authorization runs. Existing historical records retain `Paid`, `PaymentFailed`, or `PendingPayment` in reads. Preserve the `Idempotency-Key` GUID on client retries.
5. SQL `Orders` becomes historical and is not an authoritative writer. Before any new Orders PostgreSQL writes, rollback can restore legacy routing and mode. After PostgreSQL accepts new orders, reconcile every order, reservation, payment decision, and notification into SQL and Inventory before reverting ownership. Never enable both order writers simultaneously. Do not rerun the pre-cutover importer after target-only orders exist.

The development freeze imported 64 SQL orders (34 `Paid`, 30 `PaymentFailed`, zero pending), verified all 64 target orders and saga rows, and repeated the import without changes. Exact historical status strings were backfilled and verified before routing changed. The through-YARP development check passed confirmed, payment-rejected, and insufficient-inventory flows with in-memory MassTransit. A dedicated migration test copied three fixed SQL orders covering pending, paid, and failed statuses; it verified three matching item snapshots and a repeat import. A prior 54-row shared-test import passed at its original snapshot, but subsequent legacy tests changed that shared source, so the dedicated fixture is the repeatable migration gate. Docker and RabbitMQ are absent, so container startup, broker delivery/recovery, and queue behavior remain deferred.
