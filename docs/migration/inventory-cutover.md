# Inventory cutover and rollback

1. Inspect SQL stock, pending orders, Catalog product IDs, and current Inventory target rows. Resolve missing Catalog references without deleting business data. For referenced SQL products absent from Catalog, the guarded `Catalog.Migration --append-missing` mode copies only those missing GUIDs, leaves existing Catalog rows untouched, requires `CATALOG_WRITE_FREEZE_ACK=true`, and checks source stability. Review the candidate rows and order history before running it. Drain or pause new order creation, payment, and stock adjustments. Keep YARP Inventory routes and monolith `InventoryOwnership:Mode` on `Legacy` during this freeze.
2. Configure `ConnectionStrings__LegacyCommerce`, `ConnectionStrings__Catalog`, and `ConnectionStrings__Inventory`. Apply the Inventory EF migration. Set `INVENTORY_WRITE_FREEZE_ACK=true` only after write traffic is frozen. Run `dotnet run --project src/Services/Inventory/Inventory.Migration -- --import`, then `--verify`. The import fails on missing Catalog IDs, negative source stock, duplicate references, source changes during copy, or any target mismatch. It never overwrites a populated, divergent target.
3. Record source/target counts, total available stock, pending reservation IDs, and the SHA-256 source fingerprint. Repeat `--import` to prove idempotence while writes remain frozen. Do not re-import after the new service accepts writes.
4. Start Inventory with its own PostgreSQL connection and RabbitMQ configuration. Verify `/health`, reservation and stock APIs, outbox backlog, and consumer connectivity. Switch all six YARP Inventory route cluster IDs to `inventory` **together** with monolith `InventoryOwnership:Mode=Extracted` and its `InventoryService:BaseUrl`. Keep direct service ports private to trusted operators. Reopen writes only after a through-gateway order/payment check.
5. SQL `Stock` remains read-only historical data after cutover. If no new Inventory writes or reservations occurred, rollback may switch routing and monolith mode to Legacy. Once PostgreSQL has accepted writes, reconcile every change back to SQL Server before any ownership rollback. Never run two authoritative writers. A route-only rollback after new writes would lose or duplicate stock.

Failure recovery: leave the old system authoritative if import or verification fails; investigate and rerun the idempotent tool under the same write freeze. If an HTTP reserve times out, look up its stable reservation ID and retry only with the same ID. If a SQL order commit fails after a remote reservation, release that ID. If release/confirmation fails after payment commit, operations staff must reconcile the order and reservation status before retrying; the Phase 05 workflow has no durable compensation queue. RabbitMQ failures do not roll back committed stock; outbox delivery resumes when the broker returns.

Development cutover completed under a write freeze. Catalog reconciliation appended 21 missing referenced SQL product GUIDs and preserved 25 existing Catalog rows; a repeat appended zero. Inventory import and verification matched 43 SQL stock rows, zero pending orders, 46 Catalog products, and 67 available units. The six YARP Inventory routes and monolith ownership now use the extracted Inventory service. A through-gateway workflow passed paid and failed orders, retry idempotency, insufficient stock, outage handling, and compensation retry. PostgreSQL has accepted new writes, so returning ownership to SQL Server requires reconciliation of every post-cutover change. Docker Compose and live RabbitMQ delivery/recovery remain unvalidated in this environment.
