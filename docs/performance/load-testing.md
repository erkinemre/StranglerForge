# Bounded performance scenarios

Use [read-only.js](../../scripts/performance/read-only.js) for nondestructive gateway, Catalog, Inventory, and optional order reads. Set `TARGET_BASE_URL` to an isolated environment and run `k6 run scripts/performance/read-only.js`. The script uses at most five virtual users for one minute. k6 reports request rate and P50/P95/P99 from `http_req_duration`. The script also records per-route latency trends.

For order submission and saga completion, provision disposable SQL Server/PostgreSQL/RabbitMQ databases with known customer/product/stock fixtures. Set `ISOLATED_TEST_ENV=true`, `ALLOW_WRITES=true`, `TARGET_BASE_URL`, `CUSTOMER_ID`, and `PRODUCT_ID`, then run `k6 run scripts/performance/isolated-workflow.js`. The script refuses to run without those explicit guards, uses no more than three concurrent users for 30 seconds, submits stable idempotency keys, sends payment intents, and records time to a terminal order state. Never point it at shared development or production data. Prepare sufficient stock, and discard only the disposable test databases afterward.

For outbox backlog recovery and circuit breaker behavior, run the documented development fault hooks against the same isolated environment, stop/restart only its broker or dependency, and record `stranglerforge.*` backlog and circuit metrics. Do not automate destructive network faults in this repository. No throughput, latency, recovery-time, or capacity result has been measured yet. Establish thresholds after the first recorded baseline and keep raw k6 output with the run configuration.
